# Elicitation vs Emergence for capabilities

## Why
The [SPAR project](https://sparai.org/projects/f26/rec8qbsiN63iT3e8Z/)'s nominal goal is to test capabilities emergence in RL. A key distinction here is to separate elicitating capabilities already present in a pre-trained model, vs installing new capabilities.

To draw an analogy to LLMs, RL for coding could be operating as persona selection for "expert software engineer" which was already a role that the LLM was capable of mimicking. It just didn't consistently use that persona, as a lot of code would be better predicted as generated by the "bogstandard software engineer" persona.

But to answer the question of elicitation vs capabilities emergence in a satisfying way, it sure would be good to have a more concrete definition of the distinction. I had Claude [investigate this](https://github.com/chainik1125/nd-rl/blob/dan/docs/project_strategy/capabilities/REPORT.md).

## Compute budget
My favorite definition it came up with is that capability is best viewed as a reliability percentage for a given compute budget. That is, a model is 50% capable at 10k FLoPs if it can solve a problem 50% of the time using 10k or fewer FLoPs. There are a lot of good things about this definition. We can use it across a huge range of systems, varying architectures, harnesses, even generalizing to non-LLM programs that solve the same problems. I like this because it feels like it can give 'fair' comparisons across these architecture changes, in a way that pass@k numbers do not. For example, we can bump up pass@k for our proof models by providing test-time-compute via MCTS during each draw. But saying that this made the model more capable is kinda cheating IMO. It is only a real improvement in capabilities if we're getting better reliability for a given FLoPs budget. So using this definition prevents us from cheating (or fooling ourselves) like this.

That said, the flexibility can also be a downside. Making a more sophisticated harness for the same model can improve reliability for a given compute budget. But then, suppose RL is 'just' teaching the model to properly use a harness that wasn't available in pre-training. Is this really installing new capabilities via RL in a way that is meaningful to us? Or did we give the model a 'solve the problem' button, and then RL it to click that button? I think the answer lies somewhere in between for most harnesses or tools that we can provide.

So I like this definition, and plan to use X% reliability with Y FLoPs budget as my working definition of capabilities. I'll be able to set Y precisely, but the reliability level will need to be estimated by actually doing repeated runs at that compute budget (we'll get some noise, but can then use standard statistical techniques to bound X if we assume a uniform probability prior [not a completely insane prior here]).

## Alternatives considered

EDL of specific proofs, given pre-trained model and given RL'ed model. The idea is that 'new capability' should imply a much lower EDL for the RL'ed model compared to the pretrained model, while a lack of capabilities would imply similar EDL values. I'm skeptical of this, because the pre-trained model and the RL'ed model could well have equal likelihood of successfully proving a given theorem, but use different routes to prove it. This means that the EDL more says "how surprising is it that this model made this particular proof" rather than "how surprising is it that this model proved this theorem at all". I do not find the former interesting, any more than I find it an interesting choice to go north 1m then east 2m, vs east 2m then north 1m.

Directly looking at the logits after teacher-forcing a given proof through the pre-trained & RL'ed model feels almost exactly the same as EDL to me, at least in the ways that are meaningful. IE, it is testing "how surprising is this particular proof" not "how good is the model at proving this theorem". I continue to care about the latter.

Comparing pass@1 to pass@k (where k is moderately large). I don't like this because reliability 'is' a form of capability to me. The choice of k feels arbitrary, and IMO the compute budget formulation gives less room to cheat via resampling, MCTS, or other strategies. pass@k is one compute usage strategy if you have leftover compute from trying once, but I don't like privileging it.
